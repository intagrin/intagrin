# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**IntaGrin** (`src/intagrin/`) is a Python framework for building declarative, YAML-driven multi-agent LLM systems. Consumers of the framework write an `ai.yaml` (routing/agents/tools/memory), Jinja2 prompts, and vanilla Python tool functions — never programmatic graph-routing code. This repo is the framework's own source, CLI, docs site, and test suite; `examples/` (`social-media-manager/`, `travel-planner/`, ...) holds example apps built *with* IntaGrin, not part of the framework package — excluded from the framework's own `ruff check .` scope (`[tool.ruff] exclude` in `pyproject.toml`) for exactly that reason.

The CLI entry point is `inta` (console script `intagrin.cli:app`, Typer-based).

## Commands

Dependency management uses `uv`; a `.venv` and `uv.lock` are checked into the environment.

```bash
uv sync                          # install/sync dependencies into .venv
uv run pytest tests/             # run the full test suite
uv run pytest tests/test_parser.py            # run one test file
uv run pytest tests/test_parser.py::test_foo  # run one test
uv run ruff check .              # lint (matches CI)
```

CI (`.github/workflows/`) runs `ruff check .` then `pytest tests/` on Python 3.11 and 3.12, plus a separate non-matrixed job that runs the `server/templates/monitor.html` browser test suite. A second workflow runs `intagrin verify` and `intagrin eval` for continuous agent evaluation. A third deploys `docs/` (VitePress) to GitHub Pages via `npm`.

Docs site (VitePress, root `package.json`):
```bash
npm run docs:dev
npm run docs:build
```

Browser tests for the Monitor dashboard's React UI (`server/templates/monitor.html`, no build step — CDN React + Babel-standalone), via Puppeteer + Node's built-in test runner (root `package.json`):
```bash
npm run test:monitor
```

## Architecture

**`errors.py`** — the structured error-code registry (`ERRORS`, `IntaGrinError`). A small,
incrementally-growing set of high-value errors across the CLI/runtime/server layers are raised as
`IntaGrinError(code, message)` instead of plain exceptions; everything else still raises
plain `ValueError`/`HTTPException`/etc. and is unaffected. `compiler/parser.py`'s `ParserError`
and `runtime/memory.py`'s `CheckpointerConfigError` are `IntaGrinError` subclasses, so every
existing catch-all site that prints `str(e)` shows a code automatically with no per-site changes.
CLI output prefixes `Error [CODE]: ...`; FastAPI responses (both `server/api.py` and
`server/monitor.py`, via `server/error_handlers.py`) add an additive `code` JSON field alongside
the existing `detail` string. `docs/12_Error_Reference.md` and
`templates/copilot/reference_error_codes.md` are both generated from this registry by
`scripts/generate_error_docs.py` — re-run it after editing `errors.py`
(`tests/test_error_docs_freshness.py` fails CI if you forget). The Monitor dashboard's "IntaGrin
Architect" chat (`server/monitor.py`'s `run_architect`) has a `lookup_error_code` tool so it can
explain a code a user pastes in.

**`config/reference.py`** — the `ai.yaml` configuration reference, generated by walking
`AppConfig.model_json_schema()` (one section per Pydantic model, keyed by class name, plus a root
`AppConfig` section). Unlike the error registry, this needs no hand-maintained content at all — a
new field in `config/schema.py` with a `Field(description=...)` appears here automatically, and
`tests/test_config_reference.py` fails if any field lacks one. `docs/13_Configuration_Reference.md`
and `templates/copilot/reference_config.md` are both generated from it by
`scripts/generate_config_reference.py` — re-run after editing `schema.py`
(`tests/test_config_reference_freshness.py` fails CI if you forget). This module (not the script)
is what `run_architect`'s `lookup_config_reference` tool imports at runtime, since it must work
from an installed package, not just this source checkout.

**`config/json_schema.py`** — renders the raw JSON Schema for `ai.yaml` (editor autocomplete/validation
via `# yaml-language-server: $schema=...`), derived from the same `AppConfig.model_json_schema()`
as `config/reference.py` but with `additionalProperties: false` forced onto every model fragment so
a typo'd key is a schema error, not a silently-ignored Pydantic default. Lives in the package (not
`scripts/`) because `cli.py`'s `new` command imports `render_json_schema()` at runtime to scaffold a
project's `ai.schema.json`. `scripts/generate_ai_schema.py` writes its output to the bundled
`templates/ai.schema.json` copy — re-run after editing `schema.py`
(`tests/test_ai_schema_freshness.py` fails CI if you forget).

**`config/orchestration_guide.py`** — single source of truth for the `handoffs`/`delegations`/
`routers`/`auto_route`/`spawns`/`workflows` decision guide (its `GUIDE` string), replacing what used
to be duplicated by hand across `server/monitor.py`'s `run_architect` system prompt and
`templates/copilot/architect_instructions.md`. `cli.py`'s `compile` command and `run_architect` both
splice `GUIDE` into their system prompts directly; `scripts/generate_orchestration_guide.py` writes
it to `docs/03_Choosing_an_Orchestration_Primitive.md` for human readers, from where the existing
`scripts/generate_architecture_reference.py` bundles it into `templates/copilot/docs/` with no code
change of its own — re-run `generate_orchestration_guide.py` after editing this module
(`tests/test_orchestration_guide_freshness.py` fails CI if you forget).

### Compile → validate → execute pipeline

1. **`compiler/parser.py`** — `parse_project()` reads a consumer project's `ai.yaml` + `.env`, validates it against the Pydantic schema, and produces an `ExecutionGraph` (config + env vars). Results are cached by file mtime to avoid repeated disk I/O on API servers while still supporting hot reload.
2. **`config/schema.py`** — Pydantic models defining the entire `ai.yaml` surface: `ModelConfig`, `MemoryConfig`, `GuardrailsConfig`, tool configs (`LocalToolConfig`/`MCPToolConfig`/OpenAPI), `ServerConfig`, RAG config, reducers, circuit breakers, etc. This is the source of truth for what's valid in `ai.yaml` — check it before assuming a YAML key exists.
3. **`compiler/verifier.py`** — formally checks the declared handoff/routing graph for cycles and estimates worst-case run cost (`inta verify`); also nudges (never fails) toward setting `state_schema` when a project has none, since `write_state` otherwise accepts any key/type with zero validation.
4. **`compiler/exporter.py`** / **`compiler/reverse.py`** — export a project to a standalone FastAPI app (`inta export`), and reverse-compile Markdown blueprints into `ai.yaml` (`inta compile`).
5. **`runtime/engine.py`** — the core agent runtime: renders JIT Jinja2 prompts, drives the LLM loop via LiteLLM, handles handoffs/delegations/routers, memory compression, and self-healing (auto-repair of malformed tool-call JSON via a fallback model). Routing *decisions* (root/conditional router evaluation) are delegated to the pure, side-effect-free `SwarmRouter.evaluate_root_router`/`evaluate_conditional_routers` in `runtime/router.py` — `_resolve_routing` owns only the side effects (state mutation, tracing, circuit breaker, message breadcrumbs) once a router has decided. This is the largest and most central module.
   Four `circuit_breakers` fields cap cost/execution paths `inta verify`'s worst-case cost table used to report as explicitly unbounded: `max_corrector_tokens` (`max_tokens` on every self-healing corrector-model call — both malformed tool-call argument repair and `response_schema`/`spawns.result_schema` repair, previously uncapped output-side cost), `max_compression_batch_messages` (`_compress_memory` folds evicted history into `long_term_memory` in successive batches of at most this many messages instead of one unbounded prompt — bounds the input side; the summary's own output was already capped at 500 tokens), `max_parallel_tool_calls_per_turn` (caps how many ordinary tool calls from one LLM completion actually execute concurrently — calls beyond the cap get a synthetic tool-result telling the model to split the work across turns, rather than being silently gathered anyway, mirroring how a duplicate control-transfer call in the same turn is rejected rather than run), and `max_tool_result_chars` (`_cap_tool_result`, applied once in `_execute_tool_calls_with_healing`'s `run_single_tool` — every path a tool result can take, local/MCP/skill/delegation/spawn, funnels through this one point before becoming a `role: tool` message's content — truncates an oversized result with a notice instead of letting one scraped page or big API/MCP blob silently eat a large fraction of the context window; character-based, not a real tokenizer, to stay cheap on this hot path). All four now render as bounded (green "yes") in the verifier's cost table with their configured value shown (`max_tool_result_chars` is the one nullable field — set to `null` it renders unbounded, red "no", same table).
   `model.enable_prompt_caching` (default `true`) sets `litellm.enable_anthropic_prompt_caching` in `RuntimeEngine.__init__` — LiteLLM's own hook then auto-injects Anthropic-style `cache_control` breakpoints on the system prompt and trailing turn, but only for Anthropic/Bedrock Claude models that report prompt-caching support, standing down entirely for every other provider or when a request already carries client-supplied `cache_control`. Safe to leave on unconditionally; process-global like the `telemetry` callbacks it sits next to (same pre-existing last-engine-constructed-wins limitation across concurrently loaded projects). Distinct from `model.use_cache`, which is LiteLLM's semantic full-response cache, not a prompt-prefix cache.
   `model.variants` (A/B/canary model routing — a list of `{model, weight}`) is resolved once per session via `_select_model_variant` (a deterministic weighted hash of `session_id`, sticky for the whole conversation) and stored in `state["_model_variant"]`, checked ahead of `model.primary` (but behind an explicit per-agent `model_override`) at both turn-loop model-resolution sites.
   `model.cascade` (FrugalGPT-style cheap-to-expensive escalation, `list[str]`) is checked at the same two model-resolution sites, between `_model_variant` and `model.primary`, via `_resolve_cascade_entry_model` — but only ever returns non-`None` for an agent with `response_schema` set, since schema pass/fail is the only free, already-computed confidence signal this framework has for judging whether a cheaper model's answer was good enough. When it applies, the *entire* turn (including any tool calls the agent makes) runs on `cascade[0]` instead of `model.primary` — that's where the actual cost saving comes from, not just the escalation path. `_apply_response_schema` (same function that already self-heals a `response_schema` violation via a corrector-model patch) now tries a full regeneration from each remaining cascade tier first — off `current_messages`, the exact prompt the just-failed completion was generated from, now threaded through as an optional third parameter both turn-loop call sites pass — before falling back to the pre-existing corrector patch. Regeneration only ever produces a new terminal text response, never re-issues tool calls (guarded by the same `msg.tool_calls` check `_apply_response_schema` already had), so it's safe regardless of what the turn did before reaching this point. `model.primary` is always the final escalation tier (deduplicated against `cascade` itself) regardless of what's configured, so a cascade can never produce a worse ceiling than not using one at all.
   `workflows`' `vote` task type (`WorkflowTask.vote: VoteConfig`) supports multi-agent debate via `vote.debate_rounds` (default `1` — today's original single-independent-answer behavior, capped at `5`): for each additional round, `_run_debate_rounds` shows every branch every OTHER branch's current answer and appends a revision prompt to that branch's own still-live child engine (not a fresh one — a branch keeps its own prior reasoning across rounds, on top of seeing the others'), then re-runs its turn loop. Rounds run sequentially (each depends on the full previous round's answers); branches within a round still run concurrently via `asyncio.gather`, unchanged from the single-round case. Orthogonal to `vote.strategy` (`majority`/`llm_judge`), which still governs only the final aggregation step, now over the *last* round's answers — `_execute_task`'s state merge-back (`_merge_child_state`) was moved to run after every debate round completes, not right after the first, so it reflects each branch's final state too.
   `_pending_approval` (the shared HITL pause/resume state — see `errors.py`'s `AwaitingHumanInput` below) supports N-of-M multi-approver chains via `required_approvals`/`required_approvers` on a tool config and `server.auth.approvers` (named approver id → env var); `/resume` tracks `approvals_received` and only executes the tool once satisfied — single-approver `required_approvals: 1` (the default) is unchanged from before this existed. Setting both to genuinely different values is a likely mistake (`required_approvers`, when non-empty, always wins — `required_approvals` becomes dead configuration in that case, silently); `compiler/verifier.py` warns (never fails) when a tool's `required_approvals` was actually changed from its default of 1 while `required_approvers` is also set and the two don't already agree. `_approved_tool_calls` (the one-time exemption `/resume` grants a paused call once approved) is keyed by `tool_call_id`, not tool name — two concurrent calls to the same `requires_approval` tool with different arguments (two `refund` calls for different orders in one batch) are different actions, and approving one must never let the other ride along just because they share a name.
   `_execute_tool_calls_with_healing` durably caches each tool call's result in `state["_tool_call_scratch"]` (keyed by `tool_call_id`) the moment it finishes, not batched until the whole `asyncio.gather` round completes — otherwise a process interrupted mid-batch would lose every result, including ones that had already finished, and leave `self.messages` ending in an assistant message whose `tool_calls` have no matching tool-role responses (an invalid sequence that breaks the next LLM call outright). `initialize()` calls `_recover_dangling_tool_calls` on every load, which detects exactly that shape and re-runs the batch — any call already present in the scratch cache is served from there instead of re-executed, so a side-effecting tool (a refund, an email) fires at most once even across a crash/restart; the cache itself is popped once a batch's results are safely appended to `self.messages`, so it never grows past one in-flight round.
   `_resolve_routing` also calls `_record_router_trace` for every root/conditional router it evaluates, appending `{turn, kind, description, fired, target, error}` to `state["_router_trace"]` (bounded to the last 50 — a plain list ride-along on `self.state`, no new table). Before this existed, the fact that a router was evaluated but did NOT fire (or raised — most commonly a typo'd state-key name) only ever reached a live SSE `router_decision` event (`Tracer.log_router_decision`): gone forever the instant nobody had the Monitor dashboard open. `turn` mirrors `_record_usage`'s `_cost_trace` convention (`len(self.messages)` before this round's message is appended), so `inta replay` (`cli.py`) can show a "did not fire" / "condition raised" note at the exact point in the transcript it happened — filtered to non-fired entries only, since a router that DID fire already leaves a `"Router: Transferred to..."` system message and repeating it would just be noise.
   `condition_functions:` (root-level `AppConfig` list of `{name, module}`, `config/schema.py`'s `ConditionFunctionConfig`) is a closed, pre-registered name → callable whitelist that `routers[].condition`/`tools[].available_when` expressions may call by bare name (e.g. `is_eligible(customer_tier)`) — `runtime/router.py`'s `safe_eval`/`validate_condition_syntax` allow `ast.Call` only against this whitelist, with every argument itself re-evaluated through the same restricted grammar, so a condition still can never reach arbitrary code or attribute access (`state.get(...)` stays rejected). Lets a deterministic-but-non-trivial decision (a regex, a multi-field rule) stay a zero-LLM-cost `routers` hit instead of forcing a `handoffs` round-trip just to get real logic. Loaded once per `initialize()` into `self._condition_functions` (cheap — an import + getattr, no I/O — so it's not worth pooling in `SharedResources`) and threaded through every `safe_eval`/`evaluate_conditional_routers` call site, including `testing/simulator.py`'s shadow replay.
   `AgentConfig.spawns` (`spawn_agent`, dynamic runtime agent creation) is the one place the runtime creates an agent that was never in `graph.config.agents` — deliberately never mutates `graph.config.agents`/`SharedResources` in place (both are shared by reference across every concurrent session for the project); instead the new agent's definition lives in `self.state["_dynamic_agents"]` (checkpointed, session-local) and `_resolve_agent_cfg(name)` synthesizes an ephemeral `AgentConfig` from it fresh every turn — the single call site every other method now uses instead of `graph.config.agents.get(active_agent_name)` directly. A spawned agent's tools are a schema-`enum`-constrained (re-validated server-side) subset of `spawns.tool_pool`, which is itself constrained at parse time to a subset of the spawning agent's own `tools:` — privilege escalation through creation is a Pydantic validation error, not a runtime hope. A spawned agent's only control-flow option is a fixed `return_to_creator` (no handoffs/delegations of its own, no dynamic-to-dynamic edges) — see `docs/03_Dynamic_Agent_Spawning.md`. `spawns.result_schema` (optional) derives `return_to_creator`'s own tool-call schema from a Pydantic model — steering the model via constrained tool-call decoding instead of a generic free-text `summary` field — and re-validates server-side (self-healed via the same corrector-model retry as malformed tool arguments elsewhere) before accepting it, so structured data flows back to the spawning agent without any `write_state`/`read_state` choreography needed. `extract_final_answer` (shared by `spawn_agent`'s own completion, `delegate_task`, parallel workflow branches, and `/resume`'s nested-child-approval continuation) is what actually retrieves this — it checks for a `return_to_creator` tool result in addition to the last assistant message, since return_to_creator's result lands in a `role="tool"` message that a naive assistant-content-only scan would miss entirely. `spawns.on_complete` (a list of `{key, value}` state writes) applies automatically — via `_apply_spawn_completion_hooks`, reusing `apply_state_write`, the same pipeline `write_state` itself goes through — once a spawned agent genuinely completes (never on a pause, never on a `circuit_breakers.max_delegation_turns` forced abort), so a `tools[].available_when` gate can unlock declaratively instead of requiring the sub-agent's own spawn instruction to call `write_state` on `ai.yaml`'s behalf. Both completion sites (`spawn_agent`'s own synchronous path in `engine.py`, and `/resume`'s nested-child-approval continuation in `server/api.py`) call the same hook method, guarded identically against firing on a forced abort.

   `AgentConfig.delegations` compiles a `delegate_task` tool (one sub-task, one child engine) and a `delegate_to_many` tool — fan out N concurrent instances of the same already-known sub-agent, one per instruction, for an item count only known at runtime (e.g. one sub-task per city the user mentioned); capped by `circuit_breakers.max_parallel_fan_out` (default 10, rejected outright over the limit rather than truncated) since an LLM-chosen fan-out width has no natural ceiling otherwise. Both tools share `_run_delegated_child` (create one isolated child engine on a deep copy of state, run it to completion or a `max_delegation_turns` abort or a human-approval pause) — `delegate_to_many` runs N of these concurrently via `asyncio.gather` and merges each child's state back sequentially in declared (instruction) order once every child has finished, not in whatever order they happened to complete in real wall-clock time, mirroring `delegate_task`'s own `_deferred_child_merges` ordering guarantee and `run_workflow`'s identical pattern for `parallel`/`vote` branches. A child that pauses for approval mid-fan-out surfaces on the parent's `_pending_approval` exactly like `delegate_task`'s single-child case (queued behind any sibling that pauses first via `_set_pending_approval`'s existing queue) while every other instruction still runs to completion and merges normally.
   `AgentConfig.skills` (`SkillReferenceConfig` entries or bare name strings, resolved against a root-level `AppConfig.skills: list[SkillConfig]`) is the Agent Skills primitive — a progressive-disclosure answer to context rot, distinct from `inta copilot`'s own unrelated IDE-skill-folder convention under `templates/copilot/skills`. Unlike `remember_episode`/`recall_episodes` (a single global config, statically registered), a skill's availability is inherently per-agent, so `load_skill`/`read_skill_resource` follow the `spawn_agent`/`transfer_agent` pattern instead: built fresh each turn in `_get_active_tools` with a JSON-Schema `enum` over exactly that agent's own resolved skill names (`_resolve_available_skills`, which also evaluates each skill reference's own `available_when` through the same restricted grammar as `tools[].available_when`), and dispatched via a name-based special case in `execute_tool` rather than living in `self.local_tools`. `load_skill(name)`'s *tool description* is built once from every available skill's own one-line `description` field, joined — so "which skills exist and when to use one" rides along in the tool schema itself at the cost of one tool definition, never a system-prompt paragraph that's always present whether or not it's relevant. Calling it resolves `SkillConfig.path` relative to the project directory and returns the target file's full text as an ordinary tool result (a single file's content directly; a directory's `SKILL.md`, falling back to any other `.md` file) — flowing into context through the exact same mechanism any other tool result already does, no new context-injection code. `read_skill_resource(skill_name, resource_path)` is only registered when at least one available skill's path is a directory, and is path-traversal-guarded (`Path.resolve()` + `is_relative_to` against the skill's own directory) so a `../` escape is rejected, not silently followed. `compiler/verifier.py` fails (not just warns — same severity as `inta verify`'s router/available_when condition-syntax errors) when a root-level `SkillConfig.path` doesn't resolve to an existing file/directory. See `docs/15_Agent_Skills.md`.
   `tools[].available_when` (any `LocalToolConfig`/`MCPToolConfig`/`OpenAPIToolConfig`/`ToolReferenceConfig` entry) gates whether a tool is even offered to an agent this turn, using the exact same restricted condition grammar as `routers[].condition` (`runtime/router.py`'s `safe_eval`/`validate_condition_syntax`, also statically checked by `inta verify` and `validate_config_dict`) — structurally withholding a tool via `_get_active_tools` until its condition is true, not just prompting the model not to call it yet. Re-checked at execution time too (`_is_tool_allowed_for_active_agent`/`_tool_currently_available`), never trusted from the schema filter alone. Fails *closed* on a malformed condition (hides/rejects the tool) — the opposite default from a broken router condition, which fails open and just skips. A referenced state key that simply hasn't been set yet (routine — e.g. no research has happened yet in a fresh session) hides the tool quietly; only a genuine grammar violation logs an error, so a condition's normal early-session "not true yet" state doesn't spam the trace log every turn.
   `tools[].untrusted_output` (any `LocalToolConfig`/`MCPToolConfig`/`OpenAPIToolConfig`) marks a tool's return value as untrusted — the "lethal trifecta" pattern (untrusted content + access to private data/state + a way to exfiltrate). Defaults to `false` for local tools (developer-authored Python) and `true` for MCP/OpenAPI tools (an external server/API outside the project's own trust boundary), plus RAG's auto-registered `search_knowledge_base` unconditionally. `self.untrusted_tools` (populated in `_load_tool_config`, pooled through `SharedResources` like `global_tool_schemas`) is checked in `execute_tool` the moment a call succeeds — the first hit sets `state["_untrusted_content_ingested"] = true` for the rest of the session (never reset; the ingested content stays in conversation history/`long_term_memory` regardless). No new condition grammar needed: it's a plain state key, so any `available_when`/`routers[].condition` can reference it directly (e.g. `"not _untrusted_content_ingested"`) to withhold a sensitive tool once this session has seen untrusted content. `compiler/verifier.py` advises (never fails) when an agent has both an untrusted-output tool and a separately-flagged `requires_approval` tool whose `available_when` doesn't reference the key — resolving `ToolReferenceConfig` against the root-level tool it names, since that's the shape most real projects use.
6. **`runtime/tools_loader.py`** / **`runtime/tool_runner.py`** — reflect Python function signatures/docstrings into JSON schemas for LLM tool-calling, and execute tool calls (including `requires_approval` human-in-the-loop gating; the `lazy_load_tools` semantic-selection call is debounced per-turn against the recent trajectory).
   `ToolRunner.get_active_tools`'s `lazy_load_tools` selection tries a cosine-similarity embedding gate (`_select_tools_by_embedding`) before its original LLM-completion selection (`_select_tools_by_llm`, unchanged) — no completion call at all for the common case, reusing `episodic_memory.py`'s `embed_text` wrapper (which never raises, returns `None` on any provider failure) and `rag.py`'s `cosine_similarity`. Embedding model preference follows whatever the project already declared (`rag.embedding_model`, then `episodic_memory.embedding_model`, then `"text-embedding-3-small"`) rather than a new config field. The threshold is relative to each call's own score spread (`top_score - max(spread * 0.5, 0.02)`), not a fixed cosine value, with a floor of 3 tools so the heuristic never under-selects down to zero — a too-generous tool set costs a few extra schema tokens, a too-narrow one silently withholds the tool actually needed. `_select_tools_by_embedding` returns `None` (not an empty set) on *any* failure — a missing tool embedding, an unreachable embedding provider, an unresolvable model — and `get_active_tools` falls back to the original LLM-based path in that case, so this is purely additive: worst case, behavior is identical to before it existed. Tool embeddings are cached per `(embedding_model, tool-name-set)` on `engine._tool_embedding_cache` (tool schemas are static within a session); only the trajectory is re-embedded each call.
   **`runtime/sandbox.py`** (`SandboxToolConfig`, `tools[].type: "sandbox"`) runs agent-generated code in an isolated subprocess — `_load_tool_config` wraps `run_sandboxed_code` into an ordinary function registered in `self.local_tools` (so it flows through `execute_tool`'s existing local-tool dispatch, `requires_approval` gating, and circuit breakers with zero new call sites) and marks it `untrusted_output=True` by default (its stdout/stderr can be influenced by whatever the executed code does). Deliberately scoped to what stdlib can do reliably with no new dependency: a wall-clock timeout, POSIX CPU/memory rlimits (a no-op on Windows), a secret-free explicit environment (never a copy of the engine's own `os.environ`), and an ephemeral working directory — explicitly **not** a filesystem or network security boundary (no chroot/container/microVM, no firewall/namespace), documented as such in the module docstring rather than implying otherwise. `inta verify` nudges (never fails) toward `requires_approval: true` on a sandbox tool that doesn't have it.
7. **`runtime/mcp_client.py`** — spawns and talks to Model Context Protocol server subprocesses for `type: "mcp"` tools. `MCPToolManager.call_tool` always passes `allow_claimed=True` (the MCP Tasks extension, `mcp>=2.0.0`), so a server that claims a call as long-running instead of answering immediately doesn't raise — it returns a `{"_mcp_task": {...}}` sentinel instead of a flattened string; a server that doesn't support Tasks is completely unaffected (returns an ordinary `CallToolResult` exactly as before). Deliberately does **not** reuse `_pending_approval`/`/resume` for this: that queue is a single-slot FIFO that blocks all new `/chat` messages until resolved — correct for "needs a human," wrong for "a background job is running and the user should keep chatting." Instead, `execute_tool` records the claim in `state["_pending_mcp_tasks"][task_id]` (a plain ride-along dict, same convention as `_router_trace` — no new table, no special-cased crash recovery needed since the task lives on the MCP server, not this process) and returns an ordinary tool result telling the model to call the newly auto-registered `check_mcp_task_status(task_id)` — offered to an agent whenever any of its resolved tools maps to an MCP server (`_get_active_tools`/`_is_tool_allowed_for_active_agent`), dispatched via the same name-based special case in `execute_tool` as `load_skill`/`spawn_agent`. Polling reuses the *same already-connected* session (`MCPToolManager.get_task_status`/`get_task_payload` — never reconnects, since the manager's `AsyncExitStack` ties every server's lifetime together) and, once genuinely done, pops the pending entry and returns the real result (or an `IG-MCP-002`-coded failure string on a `failed`/`cancelled` status or an elapsed `MCPToolConfig.max_task_wait_seconds`, which defaults to `None` — unbounded, matching today's behavior for servers that never claim a task). `MCPToolConfig.env` is also new: extra environment variables merged over the subprocess's default environment. `compiler/verifier.py` nudges (never fails) when an MCP tool has no `max_task_wait_seconds` set.
8. **`runtime/rag.py`** — declarative vector RAG (auto-registers a `search_knowledge_base` tool when `rag:` is configured); embeddings are cached to `.ai/rag_cache.json`, keyed by (file, mtime, chunk index, model), so unchanged documents don't re-embed on every restart.
9. **`runtime/memory.py`** — pluggable conversation checkpointing: sliding-window/buffer in-process, or SQLite/Postgres/Redis backends. `build_checkpointer(mem_cfg, project_dir, strict=...)` is the single source of truth for picking a backend from `memory:` config (non-strict for `RuntimeEngine`, which should still boot on an imperfect config; strict for CLI tooling reading *existing* history, which should error rather than silently read the wrong backend). Each checkpointer also exposes `list_sessions()` for enumerating historical sessions. Postgres/Redis client libraries are optional extras (`pip install "intagrin[postgres]"` / `"intagrin[redis]"`), not hard dependencies; `postgres_connect`/`postgres_dict_cursor` (also in this module) are the shared psycopg-v3-then-psycopg2 connection helpers every other Postgres-touching module (`run_logger.py`, `rate_limiter.py`, `shared_memory.py`, `server/monitor.py`) reuses instead of hard-importing `psycopg2` directly.
   `engine.py`'s `_save_checkpoint` chains each write onto `self._pending_checkpoint_task` (the previously scheduled save) instead of firing independent unawaited `asyncio.create_task(asyncio.to_thread(...))` calls — without that ordering guarantee, a single request's several close-together saves (before the turn loop, after the assistant message, after tool results, ...) could finish out of order and a `SQLiteCheckpointer`'s last-write-wins upsert would silently clobber newer state with a stale one. `_await_last_checkpoint` lets a caller that's about to read back a checkpoint (e.g. `/resume`) wait for the real latest write first.
   `runtime/run_logger.py` mirrors this same raw-SQL, self-managing-schema style for a separate `run_logs` table (same sqlite file / Postgres connection as `checkpoints`) — one best-effort row per API-triggered `/chat`/`/chat/stream`/`/resume`/`/stream` call (cost/token deltas, cumulative totals, message count, latency), scoped to `memory.type` in `{sqlite, postgres}` only, same as `db_migrations/auto_migrate.py`. Powers the Monitor dashboard's Logs page (`GET /api/logs`).
   `runtime/rate_limiter.py` reuses that same `run_logs` table (no new schema) to enforce optional per-caller quotas (`server.rate_limit.max_requests_per_window`/`max_cost_per_caller_per_day`/`max_tokens_per_caller_per_day`) — fails open on infra errors, raises `IntaGrinError("IG-RT-008", ...)` (HTTP 429) on an actual breach; every `server/api.py` endpoint has an `except IntaGrinError: raise` guard before its generic exception handler so this (and any other codified error) isn't swallowed into a misleading 500.
   `runtime/shared_memory.py` extends `long_term_memory` (see `_compress_memory` below) to a scope broader than one session via `memory.shared_scope: session|tenant|global` — a new best-effort `shared_memory` table, last-write-wins, merged into a session's own `long_term_memory` on every `initialize()`.
   `runtime/episodic_memory.py` mirrors the same self-managing-schema convention for a new `episodes` table — append-only (many rows per scope_key, unlike `shared_memory`'s single upserted row), auto-registering `remember_episode`/`recall_episodes` tools when `episodic_memory:` is configured (same "presence triggers auto-registration" pattern as `rag:`); `episodic_memory.scope` is a separate `session|tenant|global` knob, independent of `memory.shared_scope`. `remember_episode`/`recall_episodes` are bound `RuntimeEngine` methods (need `self.session_id`/`self.state` to compute the scope key), so — like `read_state`/`write_state`, unlike `search_knowledge_base` — they must be explicitly rebound to the real session's own engine in `initialize()`'s pooled-`SharedResources` fast path, not left inside the shallow-copied `local_tools` dict.
   `semantic_search_episodes` (a `query`-based `recall_episodes` call) ranks candidates by a Generative-Agents-style blend of three `[0, 1]` signals averaged together, not cosine similarity alone: relevance (similarity to `query`, clamped at 0), recency (`_recency_score` — exponential decay from `created_at`, ~0.995/day, gentle since these episodes should matter for a whole production retention window, not one simulated day), and importance (the episode's own optional 1-10 `remember_episode` rating, clamped server-side; unrated defaults to a neutral 0.5) — so a technically-closer semantic match from months ago doesn't automatically outrank something more recent and just as relevant. `episodes.importance` is a migrated column (`_SQLITE_MIGRATIONS`/`_POSTGRES_MIGRATIONS` in `ensure_schema`, same `ALTER TABLE` guard pattern `worker.py`'s `job_queue` table uses) so a pre-existing `memory.db` from before this existed still works. `remember_episode`'s docstring is written as single-line `name: description` entries (not prose) specifically so `tools_loader.py`'s primitive docstring parser actually surfaces `importance`'s calibration guidance in the tool schema the model sees — a prose paragraph silently degrades to a generic `"Parameter importance"` placeholder with no guidance at all (see `test_remember_episode_tool_schema_documents_importance_for_the_model`).
   `_compress_error_loops` (the repeated-identical-tool-failure "mode collapse" breaker) fires a Reflexion-style connector, `_reflect_on_error_loop`, into episodic memory when `episodic_memory:` is configured — a `remember_episode(event_type="failure_pattern", tags=["reflexion", tool_name], importance=min(10, 4 + consecutive_errors))` call recording the exact failure, so the next session (or a different user hitting the same broken pattern) can `recall_episodes` it instead of rediscovering the same dead end from scratch; the injected `[SYSTEM GUARD]` message points the model at exactly that call. Fire-and-forget via `asyncio.create_task`, tracked on `self._pending_reflection_tasks` (a plain `set`, done-callback self-removing) so the task can't be garbage-collected mid-flight — the same reason `_pending_checkpoint_task` exists, but these don't need ordering/chaining since `remember_episode` writes are independent append-only rows. No-ops (checked before scheduling anything) when `episodic_memory` isn't configured, which also keeps `_compress_error_loops` safe to call with no running event loop in that case — `asyncio.create_task` requires one.
10. **`runtime/worker.py`** — distributed background worker for async workflow/task queues; pools MCP connections/tool schemas/RAG index per project across every job via `runtime/shared_resources.py`, not rebuilt per job.
11. **`runtime/shared_resources.py`** — process-level pooling (`SharedResourcesCache`) of the expensive, session-independent parts of an initialized engine (MCP connections, tool schemas, RAG index, prompts), reused across `inta serve` requests, `inta worker` jobs, and delegated/parallel sub-agents spawned mid-request, instead of rebuilding them from scratch each time.
12. **`runtime/state_reconstruction.py`** — rebuilds a faithful state-at-each-turn timeline for a historical session from its checkpointed `messages` alone (checkpoints only ever retain the *final* `state`), by replaying successful `write_state` calls through `engine.apply_state_write` (the same pure reducer `RuntimeEngine.write_state` uses). Used by `inta simulate`.

### Serving & observability

- **`server/api.py`** — production FastAPI server: SSE streaming chat, `/resume` for human-in-the-loop approvals (both the static `requires_approval: true` gate and a tool raising `AwaitingHumanInput` at runtime resolve through the same `_pending_approval`/`/resume` mechanism), `/ws/voice`. Every request to `/chat`/`/chat/stream`/`/resume`/`/stream` also writes a best-effort audit row via `runtime/run_logger.py`.
- **`server/monitor.py`** — the visual dashboard/Architect IDE (serves `server/templates/monitor.html`, a no-build-step React app) with live SSE telemetry of agent handoffs/tool calls, an Agent Playground (`/api/chat`/`/api/stream`/`/api/resume`, thin proxies to `server/api.py`'s own endpoints — instrumenting those once covers both surfaces), and a Logs page (`GET /api/logs`) for debugging API-triggered runs. `run_architect`'s system prompt splices in `config/orchestration_guide.py`'s `GUIDE`, so the Architect chat can already answer "which orchestration primitive should I use" from the same decision table `docs/03_Choosing_an_Orchestration_Primitive.md` documents — `inta new`'s next-steps output points here explicitly. A `router_decision` SSE event whose `error` is set (a condition that raised, not just evaluated false) renders as an amber "Condition never fires" toast in `monitor.html` — the one place this data was previously visible at all, and only for a client connected at that exact moment (see `_router_trace` below for the persisted version).
- **`server/a2a.py`** — mounts the A2A (Agent2Agent) protocol surface onto `server/api.py`'s existing `app`: `GET /.well-known/agent-card.json` (a static capability card built from `AppConfig.name`/`description` and `default_agent`'s resolved tool names, deliberately unauthenticated per the A2A spec's public-discovery convention) and `POST /a2a` (JSON-RPC 2.0, supporting exactly `message/send`/`message/stream`/`tasks/get`). Deliberately mounted onto the live production app rather than built as a second detached export (the way `compiler/exporter.py`'s standalone file is) — an A2A caller gets real handoffs/delegations/memory/HITL, since `message/send`/`message/stream` are thin translation layers calling `chat_endpoint`/`stream_endpoint` directly rather than a second turn-loop implementation. The one load-bearing mapping: a set `pending_action` on the resulting `ChatResponse` becomes A2A's `input-required` task state — IntaGrin's own human-in-the-loop pause *is* exactly what that state means, so `tasks/get` (and a `requires_approval` pause mid `message/send`) surfaces it directly. `tasks/get` also reports `working` while `runtime/mcp_client.py`'s `_pending_mcp_tasks` (see below) has an entry for that session, and `completed` otherwise — an A2A "context" maps 1:1 onto an IntaGrin `session_id`, with no separate A2A task store. Errors use JSON-RPC's own reserved numeric codes (`-32600`/`-32601`/`-32603`) as the wire-level `error.code` (JSON-RPC 2.0 requires a Number there), carrying the corresponding `IG-A2A-001`/`IG-A2A-002` IntaGrin code alongside as `error.data.intagrin_code`. Explicitly out of scope, documented in the module docstring and `docs/16_A2A_Interoperability.md`: push notifications, A2A-to-A2A delegated auth chains, and multi-turn binary/file artifact streaming (`message/stream` reframes IntaGrin's own token-delta/tool-call event stream as text-only status updates).
- **`tracing/console.py`** — Rich-console telemetry logging used by `inta dev`/`inta run`. `Tracer.log_cost` also carries `model`/`prompt_tokens`/`completion_tokens` (optional keyword args, additive/backward-compatible) so a single `cost` event is self-sufficient for a complete OTel GenAI span, rather than needing to correlate against the sibling `llm_exchange` event.
- **`tracing/otel_exporter.py`** — fills the gap `telemetry: ["otel"]` left open: that setting already instruments LiteLLM's own LLM API calls via `litellm.success_callback`, but has zero visibility into IntaGrin-specific concepts. This module subscribes to `EventStreamer` (the same mechanism `server/monitor.py`'s SSE endpoint uses) and maps every event type (tool results, router decisions, handoffs, agent spawns/retirement, MCP task lifecycle, cost/usage) onto OTel spans — `gen_ai.system`/`gen_ai.request.model`/`gen_ai.usage.input_tokens`/`output_tokens` where an OpenTelemetry GenAI-semconv attribute exists, vendor-namespaced `intagrin.*` attributes otherwise. Deliberately not merged into LiteLLM's own span tree (a fragile cross-library parenting hack for marginal gain) — both point at the same OTLP endpoint independently, correlated only by shared `intagrin.session_id`. `ensure_started(telemetry_options)` is called idempotently from `RuntimeEngine.initialize()`; defaults to a zero-install `ConsoleSpanExporter` (bundled in the already-core `opentelemetry-sdk` dependency) unless the standard `OTEL_EXPORTER_OTLP_ENDPOINT` env var is set, in which case the OTLP/HTTP exporter is lazily imported from the optional `intagrin[otel]` extra — missing that extra with the endpoint set raises `IG-RT-009` rather than silently downgrading to console output.
- **`testing/`** — quality tooling invoked by the CLI: `evaluator.py` (LLM-as-judge evals), `fuzzer.py` (adversarial red-team fuzzing), `synthesizer.py` (auto-generates eval cases from tool signatures), `tuner.py` (self-healing prompt auto-repair), `icu.py` ("clinical" diagnostics: token burn rate, Context Processing Index, `repeated_tool_call_rate` — the fraction of a case's tool calls whose exact `(name, args)` pair already occurred earlier in that same case, a concrete proxy for the context-distraction flavor of context rot named in 2026 agent research, computed from `EvalCaseResult.tool_call_log` in `eval_runner.py` — etc. for `inta diagnose`), `simulator.py` (Shadow Replay for `inta simulate` — re-evaluates a candidate `ai.yaml`'s routers/circuit-breakers/`requires_approval` flags against real checkpointed sessions with zero new LLM calls; a config diff touching anything that could change what the LLM generates — prompts, models, tool identity — is refused via `diff_reasons()` rather than guessed at).
  `eval_runner.py`'s `compute_routing_accuracy`/`RoutingAccuracy` aggregate every eval case that sets `expected_agent` into a routing-correctness summary — printed by `evaluator.py`'s `run_evals` (`inta eval`) whenever at least one such case exists — splitting out the subset whose `starting_agent` has `auto_route: true` (a single-hop-probe proxy for "semantic routing decided this," since eval cases are one starting agent + one message by convention). This is the previously-nonexistent baseline needed before ever replacing `auto_route`'s per-turn LLM routing call (`runtime/router.py`'s `evaluate_semantic_routing`) with a cheaper heuristic (e.g. the same embedding-similarity fast-path pattern `ToolRunner._select_tools_by_embedding` already applies to `lazy_load_tools`) — that swap must not regress this number, and there was previously no way to even know what it was.
- **`db_migrations/`** — Alembic migrations for the framework's own persistence (checkpointer/session storage); `inta db` is a Typer sub-app (see `cli.py`) wrapping Alembic commands.

### CLI (`cli.py`)

Single Typer app (`app`) with one function per `inta <command>` (e.g. `new`, `dev`, `run`, `worker`, `compile`, `verify`, `simulate`, `fuzz`, `synth`, `tune`, `export`, `import`, `diagnose`, `eval`, `deploy`, `serve`, `monitor`, `architect`, `replay`, `copilot`), plus a nested `db` Typer sub-app for migrations. When adding a new CLI command, follow the existing `@app.command(name=...)` pattern in this file.

`new`'s non-wizard scaffold writes a `schemas.py` (a starter `AppState` Pydantic model, every field optional) and wires `state_schema: "schemas.AppState"` into the generated `ai.yaml` by default — costs nothing unfilled, and means a fresh project starts with `write_state` validation on rather than needing a developer to discover the option later (see `compiler/verifier.py`'s nudge above for a project that doesn't have one). `new --template coding-agent` scaffolds a second, real starting point — the architect/coder/verifier self-healing handoff loop from `docs/05_Example_Coding_Agent.md` — validated via `validate_config_dict` before anything is written (`tests/test_cli.py` also asserts it stays valid). `new --withagent`'s LLM-generated `ai.yaml` goes through the same `validate_config_dict` check via `_generate_and_validate_wizard_config`, self-healing up to 2 retries by feeding the corrector model the exact validation errors (the same corrector-retry shape used for malformed tool-call arguments in `engine.py`) before falling back to the default template — previously this wrote whatever JSON the model returned straight to disk the moment it merely parsed as JSON, with no schema check at all.

`replay` (time-travel debugging over a checkpointed session) also renders `state["_router_trace"]` entries (see `runtime/engine.py` above) inline at the message index they occurred, for any router that didn't fire or raised — the only place that's visible after the fact instead of only live.

## Framework conventions (apply to code this repo scaffolds/generates for consumers, e.g. via `inta new`, `inta copilot`, or example apps)

Per `src/intagrin/templates/copilot/architect_instructions.md` (the source `inta copilot` renders into `.cursor/rules/intagrin-agent.mdc` and equivalents for other IDEs — not committed in this repo itself, regenerate on demand with `inta copilot`), these govern any IntaGrin *application* code (scaffolding templates in `cli.py`, the exporter, and the example apps under `examples/`):

- No programmatic graph routing (no LangChain/LangGraph-style code) — orchestration, routing, memory, and guardrails belong declaratively in `ai.yaml`.
- Custom logic and external API integrations are plain Python functions in `tools/*.py` with type hints and docstrings (parsed into JSON schemas); for external REST APIs prefer `type: "openapi"` over hand-written wrappers.
- Prompts live in `prompts/*.jinja2`; use `lazy_load_tools: true` on an agent for semantic tool retrieval instead of dumping all tool schemas into context.
- `ai.yaml` root requires `name`, `version`, `default_agent`. Model strings use LiteLLM provider prefixes (`gemini/...`, `openai/...`, `anthropic/...`).
- Agent control flow: `handoffs` (conversational transfer, compiled to a `transfer_agent` tool), `delegations` (spawns an isolated child engine for a sub-task), `routers` (deterministic Python conditions that bypass the LLM), `auto_route: true` (semantic swarm/group-chat routing).
- Mark high-risk tools with `requires_approval: true` (gates every call); for a runtime decision (only some calls need review), raise `AwaitingHumanInput(prompt=..., context=...)` (`intagrin.errors`) from inside the tool instead — same pause/resume mechanism.
- For an agent that needs to *execute* code it (or an LLM) generated — not just write/review it — use `type: "sandbox"` (`runtime/sandbox.py`) instead of a hand-written subprocess call in a local tool. It runs in an isolated process with a wall-clock timeout, POSIX CPU/memory rlimits, and a secret-free environment, but is explicitly **not** a filesystem or network security boundary — pair it with `requires_approval: true` for anything not fully trusted (`inta verify` nudges on this).
- Suppress intentional `0.0.0.0` server bindings with `# nosec B104` for Bandit.
